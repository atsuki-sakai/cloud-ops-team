# AI が書く Python コードの品質をフックで固定する仕組み（cloud-ops-team）

* **Author:** Atsuki Sakai
* **Date:** 2026-11-25

## Overview

cloud-ops-team（Google ADK のエージェント。`app/` に約1万行の Python）で、AI が書くコードの書き方を毎回同じにしたい。対象は次の4つです。

- 厳密な型
- 決まった例外処理の形
- セキュリティ上危ない書き方を書かせないこと
- 遅い書き方（ループの中で外部 API を1件ずつ呼ぶ N+1 など）を書かせないこと

仕組みは次の3つでできています。

1. **書き方の手本になるプロジェクト Skill**（`.claude/skills/`）。AI はこれを読んでから書きます。
2. **編集直後のフック**（PostToolUse）。編集したファイル1つだけを1秒以内で検査し、違反があれば理由と直し方を返して、AI に直させます。書き込み自体は止めません。
3. **応答終了前のフック**（Stop）。時間のかかる型チェックをここで行い、最後の検査とします。

成功の基準は、わざと書いたダメなコードを、すべてのルールが実際に指摘できることです。

これまでに決まったこと：

- 編集したファイルにもとからあった違反も、AI に直させる（リファクタリングを含めてよい）。
- 例外処理は「層によって正しい形が違う」という今の方針を固定の型にする。
- `architectural-checker` は残す。
- `rust-strict-check` は削除済み（プラグイン本体、マーケットプレイスの登録、キャッシュ）。

## Analysis

7つの観点のレビューを集めて、重複をまとめた結果です。重い順に並べています。

### 1. 「ファイル全体を直させる」と、プロジェクトのルールや変えてはいけないコードがぶつかる（7観点すべてが指摘）

- **CLAUDE.md との矛盾**：`CLAUDE.md:72` には「頼まれたコードだけを変える」とあります。フックは逆のことを求めるので、AI は毎回2つの矛盾した指示を受け取ります。
- **最初の1回が大きくなる**：厳しいルールを入れると、`app/tools/issues.py`（1026行）の1行を直しただけで、違反が数十〜数百件出ます。AI が少しずつ直すと、編集のたびに残りの一覧がまた返ってきます。トークンは違反数の2乗に近い勢いで増え、直した結果また新しい違反が出る、という繰り返しも起きます。
- **変えてはいけないコードまで直してしまう**：`app/core/fingerprint.py:43` の `hashlib.sha1(...)` は、ruff の S324 に引っかかります。普通の直し方（sha256 に変える）をすると指紋の値が変わり、「指紋の式を変えない」ルールを破ります。その結果、すでに起票した Issue がもう一度起票されます。

**解決策（全員一致）**

- フックを有効にする前に、リポジトリ全体を1回だけきれいにする PR を別に出す。
- そのうえでフックを有効にする。それ以降は「ファイル全体を直す」と「頼まれた箇所だけ直す」がほぼ同じ意味になります。
- `CLAUDE.md:72` に、フックが指摘した違反を直すのは例外である、と明記する。
- `fingerprint.py` は、S324 を個別に無視するか、出力が変わらない `usedforsecurity=False` だけを直し方として認める。指紋の値が変わらないことを確かめるテストも置く。

### 2. ルールの置き場所によって、CI が落ちるか、CI とフックの判定がずれる（5観点）

- CI は `ruff check .`、`ruff format --check .`、`ty check .` をリポジトリ全体にかけています（`.github/workflows/ci.yml:32-36`）。
- 厳しいルールを `pyproject.toml` に入れると、次の PR で CI が既存コードの違反で落ちます。つまり「CI は範囲外」は成り立ちません。
- 反対に、フック専用の設定に分けると、AI にだけ厳しく、人や CI は緩いままになります。

意見は2つに分かれました。

- **案 A（一本化）**：1で書いた「全体をきれいにする PR」の後で、ルールを `pyproject.toml` に入れる。フック・CI・`make lint` が同じ設定を読むので、判定がずれません。（必要最小限・発想転換・構造の観点）
- **案 B（段階的に締める）**：`pyproject.toml` を継承した厳しめの設定ファイルを別に作り、フックだけに当てる。ディレクトリごとにきれいになったものから `pyproject.toml` に移す。（設計・実装準備・コードベースの観点）

### 3. 例外処理の「層」は、ディレクトリで決められない（6観点）

**「内部のコードは必ず投げ直す」は事実と違います。** `app/core/synthetic.py:581` と `:623` は `core/` の中にありますが、`Exception` を受けて結果を返しています。境界として働いている場所は、ほかにもあります。

- `app/agent.py:132`
- `app/routing.py:307`
- `app/providers/gcp/client.py:119`
- `app/providers/__init__.py:50`

パスで判定するルールにすると、正しいコードが初日から5か所以上違反になります。

**境界での例外メッセージの扱いも、場所によって違います。**

| 例外の文字列（`str(exc)`）の扱い | 場所 |
|---|---|
| 捨てている。理由は「認証情報や URL が含まれうる」 | `app/workflows.py:232` |
| そのまま返している | `app/tools/cloud.py:26`、`app/tools/threat_intel.py:251`、`app/providers/gcp/client.py:122`、`app/integrations/github.py:107` |

「境界ではエラーの辞書を返す」という形だけで判定すると、この漏えいまで正しいと認めてしまいます。なお、`tests/unit/test_providers.py:152` は、返ってきたメッセージに例外の文字列が入っていることを前提にしています。

**提案：独自ルールを作らず、ruff の既存ルールで足りる部分を使う**

| 役割 | 使うもの |
|---|---|
| 投げ直すときに `from exc` を付けさせる | B904（すでに有効） |
| 広すぎる `except` を見つける | BLE001 |
| 境界のファイルだけ許可する | `per-file-ignores` |
| 残る正当な場所を許可する | 理由付きの `# noqa: BLE001 <理由>` |

独自の ast-grep ルールは、「境界が返すエラーの辞書に `str(exc)` や `{exc}` を入れない」という1本に絞ります。秘匿化には `app/core/redact.py` を使います。

**ただし、例外メッセージを返すかどうかは書き方ではなくセキュリティの判断です。ルールを書く前に決める必要があります。**

### 4. N+1 を構文だけで見るルールは、正しいコードを止め、本物を見逃す（6観点）

**問題のない箇所まで止めてしまう例**

- `issues.py:251`：決まった2値 `("open","closed")` のループ。
- `gcp/client.py:166`：ページ送り。
- `issues.py:104`：キャッシュ付き。GitHub にはまとめて取得する API もありません。
- `app/core/synthetic.py:413-427`：Playwright の待ちを順に行う処理。

**本当に1件ずつ呼んでいる例（約7か所）**

- `app/tools/security.py:226`、`:285`、`:894`、`:946`
- `app/tools/repo.py:114`、`:169`、`:185`

**見逃す例**

- `rollouts.py:184`：ヘルパーを経由して、1リビジョンあたり4回呼んでいる。
- `issues.py:572`：内包表記の中で呼んでいる。
- `workflows.py:230`：`getattr` で動的に呼んでいる。

**よくある直し方も、別の問題を起こします。** `asyncio.gather` で並べるだけだと、上限なしで並列に呼ぶことになり、GitHub の二次レート制限に当たります。

**提案**

- API を呼ぶ関数の一覧（`gh_rest`、`gcp_list`、`httpx.*`、名前の付いたラッパーなど）を作り、ループや内包表記の中でそれを呼んだときだけ指摘する。
- 決まった値の並びをループする場合と、ページ送りは除外する。
- 差し戻さず、警告だけにする。理由付きのコメント（`# n+1: bounded <上限>`）があれば通す。
- 本物の N+1 は、テストで API の呼び出し回数を数え、件数に比例して増えたら失敗にする。

### 5. 既にあるものと重なっている（必要最小限の観点など）

- **ADK のツールの形**：`tests/unit/test_providers.py:156` の `test_agent_tools_follow_adk_conventions` が、登録済みのツールすべてについて docstring・型ヒント・デフォルト引数の禁止を確かめています。ast-grep でファイルの場所から推測するより正確なので、足りない点はこのテストに追加します。
- **architectural-checker の中身**：プロジェクトごとに ast-grep のルール集を登録して実行する仕組みです。cloud-ops-team はまだ登録されていません。独自の ast-grep ルールをここに載せれば、実行の仕組み、出力、スナップショットテストを1つにまとめられます。ただし、Python のルール集を載せられるかはまだ確かめていません。
- **bandit / semgrep**：ruff の S 系ルールが bandit の大半を移植しています。semgrep は起動だけで1秒を超えます。どちらも入れません。

### 6. フックそのものの作り（実装準備・設計の観点）

**終了コードの使い分け**

- 終了コード 2 を返すのは、本当の違反のときだけにする。
- ツールが見つからない、フックが異常終了した、時間切れになった、といった場合に 1 や 127 で終わると、AI には何も届きません。誰も気づかないまま、すべてが通ってしまいます。
- そこで、こうした失敗は終了コード 0 で終え、JSON の `systemMessage` でユーザーの画面に表示する。

**ツールの呼び出し方**

- ツールは `.venv/bin/...` を絶対パスで直接呼ぶ。`uv run` は起動に時間がかかるので使わない。
- ast-grep は、版を固定して `lint` の追加依存（`ast-grep-cli`）に入れる。今はグローバルの `~/.cargo/bin` にしかなく、フックに渡る PATH に入っていない場合があります。

**フックがやらないこと、出す情報**

- フックでは自動修正（`ruff --fix`）をしない。ファイルが AI の知らないうちに書き換わると、次の編集が失敗します。
- 出力の形を決める。先頭に `[py-quality]` のような見出しを付けて、architectural-checker の出力と区別する。違反ごとに次の情報を出す。
  - 場所
  - ルールID
  - 理由
  - 直し方
  - 許される無視の書き方
- もとからあった違反か、今回の編集で増えた違反かも分けて表示する。出力は20件程度までにする。

**対象にする編集ツール**

- matcher に MultiEdit を加える。
- Bash で直接書き換えた分は、Stop フックで `git diff` を見て拾う。

**Stop フック**

- `stop_hook_active` を見て、やり直しの回数に上限（2回程度）を設ける。直せない ty のエラーが残ると、応答がいつまでも終わらなくなるためです。
- 対象のファイルは `git diff --name-only` と、まだ追跡していない `.py` から決める。フックの間で状態を受け渡すファイルは作らない。
- ruff と ast-grep も Stop フックでもう一度回す。ファイル1つあたり約0.08秒で、これを最後の検査にする。

**止めるスイッチ**

- `CLOUD_OPS_PYCHECK=off|warn|enforce` で、検査を止めたり、警告だけにしたりできるようにする。最初は warn で出し、件数を確かめてから enforce に切り替える。

**ログ**

- 実行ごとに1行のログを残す。内容はファイル名、ルールID、件数、かかった時間、何回目のやり直しか。
- 同じ違反が繰り返し出ていることを見つけられるようにする（`CLAUDE.md:79` の「同じエラーが3回以上出たら原因を直す」と同じ考え方）。

**1秒の予算**

- 同じイベントのフックは並列に走ります。そのため、ユーザーが実際に待つ時間は architectural-checker（最大60秒）で決まります。
- ty を1秒に収めるために後ろへ回す意味が本当にあるかは、Claude Code を通した端から端までの時間で測り直します。
- ty はリポジトリ全体でも1ファイルでも時間がほとんど変わらない可能性があるので、それも測ります。

### 7. ruff ルールの選び方（コードベースの観点）

- `--select ALL` は使わず、使うルールを1つずつ書き出す。ALL には、互いに矛盾するルール（D203/D211、COM812/ISC001 とフォーマッタ）が含まれます。ruff を上げるたびにルールが増え、そのたびに触ったファイルが全部リファクタリング対象になります。
- 入れて意味のあるルール：S、BLE、TRY（一部）、SIM、RET、PTH、TID、ANN（ANN401 を除き、`allow-star-arg-any = true`）。
- 入れても役に立たない、または害があるルール：

| ルール | 理由 |
|---|---|
| PERF203 | Python 3.11 以上を対象にしていると発動しない |
| ASYNC | 同期関数の中の同期 `httpx` 呼び出しは見つけられない |
| D417 | ADK が渡す `tool_context` の説明まで docstring に求めてしまう |
| TRY003 / EM | 該当が約91か所ある |
| COM812 / ISC001 | フォーマッタとぶつかる |

- 例外的に許可するもの：
  - `tests/**` では S101 と INP001
  - `scripts/**` では INP001
  - 2つの token ヘルパーでは S603 と S607
- ty の `python-version = "3.10"`（`pyproject.toml:72`）を 3.11 に直す。プロジェクトは 3.11 以上が前提なので、このままでは誤ったエラーが出ます。そのあと、無視しているルールを1つずつ有効にする。

### 8. Skill とルールのずれ・優先順位（わかりやすさ・構造の観点）

**Google Python Style Guide とこのリポジトリのぶつかり**

| 項目 | Google Python Style Guide | このリポジトリ |
|---|---|---|
| 行の長さ | 80桁 | 88桁で、E501 は無視 |
| import の書き方 | モジュール単位でしか import しない | ADK のツールは実体を import する（`CLAUDE.md:77`）。`from app.x import y` も多用 |

**提案**

- Skill の冒頭に優先順位を書く：フックのルールと CLAUDE.md → この Skill → `google-agents-cli-adk-code` → Google Style Guide。
- Google Style Guide と違う点は、理由付きで一覧にする。

**ずれをなくす方法**

- 直し方の説明は、ast-grep ルールの `message` と `note`、ruff のルールIDだけに書く。
- Skill はルールIDを挙げるだけにして、内容を書き写さない。
- Skill に載っているルールIDと、設定に実在するルールIDが一致しているかを確かめるテストを置く。

**参照する Skill の置き場所**

- `google-agents-cli-adk-code` は、グローバル（`~/.claude/skills/`、`~/.agents/skills/`）にしかありません。他の環境にあるとは限らないので、依存先にはせず、版を書いたうえで参照するだけにします。

### 9. テストの作り方（全観点）

**いちばん大事な問題**：わざと違反させたサンプルを `.py` で置くと、CI もフックも引っかかります。フックは AI に「直せ」と言うので、サンプルが壊されます。

**3段に分けてテストする**

1. **ast-grep のルール**：`sg test` で、YAML の中に正しい例とダメな例を直接書く。`.py` ファイルは作らない。誤検知を防ぐ「通るべき例」として、本物のコードを使う。
   - `cloud.py:_call`
   - `synthetic.py:404`
   - `issues.py:251`
   - `issues.py:104`
2. **ruff の設定**：ruff 自体ではなく、設定の正しさを確かめる。サンプルは除外したディレクトリ1か所に置き、ruff・ty・codespell・pytest のすべてで除外する。フックは `--force-exclude` 付きで呼ぶ。テストでは、ルール群が有効になっていること、許可したパスでは発動しないことを JSON 出力で確かめる。
3. **フックそのもの**：標準入力に偽の JSON を渡して、スクリプトを実行する。確かめる場合は次のとおり。
   - きれいなファイル → 終了コード 0
   - 違反がある → 終了コード 2 と、決めた形の出力
   - `.py` 以外、存在しないファイル、リポジトリの外のパス、壊れた JSON、ツールが見つからない → 終了コード 0 でログに残る
   - Stop フックのやり直し回数が上限に達した → 終了コード 0

3つとも `pytest tests/unit` に入れて、CI でも回します。

### 目指す最終形（Ideal Final Result）

- 既存の違反がほぼゼロなので、フックは「今の編集で増えた問題」だけを返す。厳しさと差分の小ささがぶつからない。
- 境界はコードの中に印として書いてあるので、構文だけのルールでも正確に判定できる。
- 外部 API の呼び出しは、数少ない決まった関数を必ず通る。N+1 は、構文と実行時の回数の両方で見える。
- Skill、フック、`make lint`、CI がすべて同じ設定を読むので、判定がずれない。

## Goals vs. Non-Goals

### やること

- 書き方の手本になるプロジェクト Skill を作る。内容はプロジェクト固有のルール、優先順位、Google Style Guide と違う点の一覧、ルールIDの索引。
- 編集直後の PostToolUse フックを作る。編集した `.py` だけを対象に ruff と ast-grep を回し、違反があれば終了コード 2 で理由と直し方を返す。1秒以内を目標にする。
- Stop フックを作る。ty と、ruff・ast-grep の再チェックを回し、やり直しの回数に上限を設ける。
- 厳しめの ruff ルール群を1つずつ書き出し、パスごとに例外を設ける。
- 例外処理のルールを作る。BLE001、B904、境界の印、例外メッセージを返さないための ast-grep ルール1本。
- N+1 は警告だけにするルールと、テストで呼び出し回数を数える仕組みにする。
- ルール・設定・フックの3段のテストを作り、`pytest tests/unit` に入れる。
- フックを有効にする前に、全体をきれいにする PR を出す。
- `CLAUDE.md:72` に例外を書き足す。
- ty の Python のバージョンを直す。
- ruff・ty・ast-grep の版を固定する。

### やらないこと

- 書き込み自体を止めること（PreToolUse で止める方式）。
- フックによる自動修正。
- bandit と semgrep の導入。
- ADK のツールの形を ast-grep で検査すること（既存のユニットテストを広げる）。
- NotebookEdit への対応（このリポジトリにノートブックはありません）。
- 人や他の AI ツールが書いたコードを、フックで止めること（これは CI の役目）。

## Alternatives Weighed

- **`--select ALL` を使う**：作成者が却下。互いに矛盾するルールがあり、ruff を上げるたびにルールが増えます。
- **例外処理の層をディレクトリで判定する ast-grep ルール**：作成者が却下。`app/core/synthetic.py:581` と `:623` のように、ディレクトリと役割が一致しない場所があります。
- **N+1 を構文で検出し、違反として差し戻す**：作成者が却下。誤検知と見逃しが多く、AI がルールをすり抜けるためにコードをねじ曲げる原因になります。警告だけにする形に変えました。
- **ADK のツールの形を ast-grep で検査する**：作成者が却下。既存の `test_agent_tools_follow_adk_conventions` の方が、実際に登録されたツールを正確に見られます。
- **bandit / semgrep**：作成者が却下。ruff の S 系ルールと重なります。semgrep は起動だけで1秒の予算を超えます。
- **PreToolUse で書き込み自体を止める**：作成者が却下。ty は標準入力からの検査に対応していません。書いた直後に直させれば十分、という判断です。
- **フックで `ruff --fix` を自動でかける**：作成者が却下。AI が持っているファイルの内容が古くなり、次の編集が失敗します。
- **案 B：フック専用の厳しい設定から、段階的に `pyproject.toml` へ移す**：作成者が却下。設定が2か所に分かれ、フックと CI の判定がずれる期間が続くためです。
- **独自の ast-grep ルールを architectural-checker に載せる**：作成者が却下。このプロジェクトのルールは、このリポジトリの中に置いて管理したいためです。
