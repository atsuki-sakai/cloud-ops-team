## 追加レビューの指摘と対応状況

### A01 — P1: 別リポジトリの参照 PR が修正の証拠に混ざる

対象: [Issue・PR ツール](../app/tools/issues.py#L819)

- **現状:** Issue に言及した PR を番号だけで扱います。別リポジトリの PR がマージされても、修正候補のマージ日時に入ります。詳細取得は設定したリポジトリの同番号 PR を参照します。
- **影響:** 関係のない変更・CI・マージ日時を根拠に、修正を検証済みと判断するおそれがあります。実モデルによる誤クローズまでは再現していません。
- **暫定対処:** 修正確認は `OPS_DRY_RUN=true` で実行し、対象リポジトリ・修正内容・CI・配置と再発状況を人間が確認してください。`OPS_AUTO_CLOSE_ISSUES=false` だけでは `ops:verified` ラベルとコメントの付与を止められません。
- **修正案:** PR をリポジトリと一意な ID で識別し、単なる言及と解消関係を分けます。別リポジトリの PR を扱う場合も、そのリポジトリから詳細を取得します。[GitHub の参照イベント仕様](https://docs.github.com/en/graphql/reference/issues#crossreferencedevent)

### A02 — P2: 複数実行が重なると重複起票・再発コメントが発生する

対象: [起票と再発報告](../app/tools/issues.py#L304)

- **現状:** 標準入口は同一実行内の通常起票を排他制御しますが、既存 Issue の検索と作成、クールダウン確認とコメント投稿の間に、別実行と共有する排他制御はありません。
- **影響:** 別インスタンスなどが同じ検索結果を読んでから書き込むと、同一障害の Issue や同じ期間の再発コメントが複数できます。単一 ADK 実行内の同期ツールが並列に動くという問題ではありません。
- **暫定対処:** 同じ監視対象へ起票するすべてのサービス・手動実行の重なりを避け、重複を確認してください。インスタンス数を 1 に減らすだけでは、他の起票元を含む保証にはなりません。
- **修正案:** リポジトリ・プロバイダー・監視対象・フィンガープリントごとに共有の排他制御と操作記録を設けます。投稿後に応答を失った場合も、再試行で二重投稿しないようにします。

### A03 — 解消済み: 実行ごとの起票上限が次の依頼へ持ち越される

対象: [実行予算](../app/core/run_budget.py#L35)、[分析ツールの境界](../app/tool_scope.py)、[回帰テスト](../tests/unit/test_routing.py)

- **以前の問題:** セッション状態の起票数が次の依頼に残り、上限到達後の新しい調査でも起票を省略していました。
- **対応済み:** PR #6 の標準 `ScheduledRouter` 入口で実行単位の予算を作成し、複数担当で共有します。同じセッションの次の依頼では 0 から開始します。同一実行内の通常起票は排他制御します。
- **検証範囲:** 同一セッションの次の実行で予算をリセットする回帰テストがあります。実行間の重複防止（A02）とレポート起票への共通予算の適用（A04）は別の未修正項目です。

### A04 — P2: レポート起票は上限と実行内の重複防止を使わない

対象: [レポート発行](../app/tools/issues.py#L391)

- **現状:** `publish_report` は `OPS_MAX_ISSUES_PER_RUN` の確認・更新をしません。同じ実行で繰り返し呼ばれると、同じレポートも複数作成できます。
- **影響:** 新規 Issue の総数が設定上限を超えることがあります。
- **暫定対処:** この上限をレポートを含む厳密な上限として扱わず、作成数を確認してください。書き込みを制限する必要がある場合は dry-run を使います。
- **修正案:** すべての起票経路で実行予算を共有し、同じ実行・同じ種類のレポートを二重作成しない操作記録を追加します。別枠を設けるなら設定と上限を明示します。

### A05 — P2: サービスアカウント鍵の監査が最初の 60 個に限られる

対象: [サービスアカウント鍵の監査](../app/providers/gcp/security.py#L226)

- **現状:** サービスアカウントを一覧取得しても、鍵を調べるのは最初の 60 個です。未調査件数や監査不完全の状態を返しません。
- **影響:** 61 個以上ある場合、後続のアカウントの長期鍵を見落とし、指摘なしと報告することがあります。
- **暫定対処:** 全サービスアカウントの一覧と鍵を別途確認してください。指摘がないことを、全アカウントを調べた証拠にしないでください。
- **修正案:** 全件を調査するか、制限が必要な場合は未調査の対象・件数と監査不完全の状態を返します。

### A06 — P2: Cloud Run の IAM 取得失敗が非公開扱いになる

対象: [Cloud Run の公開状態の監査](../app/providers/gcp/security.py#L288)

- **現状:** 公開権限の取得に失敗しても `public:false` の初期値が残り、取得エラーが結果に残りません。
- **影響:** 権限不足やタイムアウトで未確認のサービスを、確認済みの非公開サービスとして扱うことがあります。
- **暫定対処:** 公開状態は IAM ポリシーを取得できる権限で別途確認してください。API の取得成功を確認できない結果から非公開と判断しないでください。
- **修正案:** 未確認を公開・非公開と区別し、取得エラー、確認済み件数、監査不完全の状態を返します。

### A07 — P2: MySQL の有効な IAM 認証を無効と判定する

対象: [Cloud SQL の IAM 認証判定](../app/providers/gcp/security.py#L597)

- **現状:** MySQL にも PostgreSQL 用の `cloudsql.iam_authentication` を使って判定します。MySQL の正式なフラグは `cloudsql_iam_authentication` です。
- **影響:** MySQL で IAM 認証が有効でも、無効という指摘が出ます。PR #4 で修正した MySQL の PITR 判定とは別の問題です。
- **暫定対処:** MySQL の指摘は、実際のエンジンとフラグを確認して判断してください。[Google Cloud の MySQL 設定手順](https://docs.cloud.google.com/sql/docs/mysql/create-edit-iam-instances)
- **修正案:** エンジンごとの設定を共通の認証状態へ変換してから判定し、未対応のエンジンは未確認とします。

### A08 — P2: IAM の期限・条件が監査結果から失われる

対象: [IAM の取得と判定](../app/providers/gcp/security.py#L108)

- **現状:** IAM ロールの付与条件を結果に保持せず、ロールとメンバーだけで評価します。
- **影響:** 期限切れ、またはリソースなどで制限された権限を、現在の無条件の強い権限として報告することがあります。
- **暫定対処:** 権限の指摘には元の IAM ポリシーの条件を合わせて確認してください。任意の条件式は、対象リクエストの条件を踏まえた確認が必要です。
- **修正案:** 条件を保持し、単純な期限は失効を判定します。評価できない条件は条件付き権限として確認対象にします。[IAM Binding の条件仕様](https://docs.cloud.google.com/iam/docs/reference/rpc/google.iam.v1)

### A09 — P2: 期限切れの SQL 許可ネットワークを全世界公開と報告する

対象: [Cloud SQL の許可ネットワーク判定](../app/providers/gcp/security.py#L450)

- **現状:** 許可ネットワークの値だけを取り出し、`expirationTime` を失います。
- **影響:** 公開 IP が有効なインスタンスに期限切れの `0.0.0.0/0` が残っていると、現在の全世界公開として critical の指摘を返します。
- **暫定対処:** 指摘に含まれるネットワークの有効期限を確認してください。失効した設定の整理と、現在の接続許可は分けて判断します。
- **修正案:** 期限を保持し、現在有効な許可で判定します。不正な期限は未確認として扱います。[Cloud SQL の ACL 仕様](https://docs.cloud.google.com/sql/docs/postgres/admin-api/rest/v1/instances)

### A10 — P2: 標準デプロイの A2A カードが接続できない URL を示す

対象: [A2A カード生成](../app/app_utils/a2a.py#L104)、[デプロイ環境変数](../scripts/gcp/deploy_env.py#L14)

- **現状:** `APP_URL` 未設定では `http://0.0.0.0:8000/a2a/app` を示します。標準デプロイは `APP_URL` を渡さず、コンテナの待受ポートも 8080 です。
- **影響:** カードから接続先を見つける A2A クライアントが、配置したサービスへ接続できません。
- **暫定対処:** A2A を利用する場合は、配置後に Cloud Run の `APP_URL` を実際のサービス URL に設定し、カードの URL を確認してください。再デプロイで環境変数が置き換わるため、その都度確認が必要です。
- **修正案:** 初回配置で判明するサービス URL を `APP_URL` に設定し、カードと実際のエンドポイントの一致を検証します。

### A11 — P2: 独自のプロジェクト情報ファイル設定がデプロイで消える

対象: [デプロイ環境変数](../scripts/gcp/deploy_env.py#L39)

- **現状:** `OPS_CONTEXT_FILE` を設定しても、標準デプロイはその値を渡しません。配置先では既定の `config/ops-context.md` を使います。
- **影響:** 独自パスのファイルがイメージ内にあっても、ローカルで使ったプロジェクト固有情報や除外方針が配置先の指示に入りません。
- **暫定対処:** イメージに含まれる既定パスのファイルを使うか、配置後に Cloud Run の `OPS_CONTEXT_FILE` を設定してください。再デプロイで環境変数が置き換わるため、設定を再確認します。手元だけのファイルは配置先から読めません。
- **修正案:** 設定を配置へ渡し、指定ファイルの存在と読み込みを検証します。ローカルと配置で同じ設定定義を使います。

## 利用条件によって生じるリスク

### R01: 調査できなかった理由が実行後に残らない

対象: [トリガー処理](../app/fast_api_app.py#L87)、[セッション保存](../app/app_utils/services.py#L57)

固定された SDK は、実行が例外なく終了すると HTTP の成功応答を返します。権限不足などで調査できなかったという最終説明は応答に含まれず、既定のセッションはメモリ内です。
PR #6 で工程・取得不足・証拠のハッシュを構造化ログに残す処理は追加されましたが、最終結果と理由の永続台帳はありません。
Issue も作られずインスタンスが終了した場合、調査不能の最終説明を後から確認できないことがあります。HTTP 成功は監査完了の証拠にはなりません。SDK の成功応答自体は仕様です。

**暫定対処:** 運用者が最終結果を確認・保存する経路を用意してください。**改善案:** 実行 ID、調査範囲、未確認項目、エラー、秘密値を伏せた最終結果を永続保存し、「実行された」と「監査が完了した」を別の状態にします。

### R02: 複数利用者の A2A セッション所有権が分離されない

対象: [A2A のリクエスト処理](../app/app_utils/a2a.py#L118)

現在の構成は Cloud Run で認証された利用者を SDK のセッション所有者へ伝えず、既定の変換処理は `context_id` から所有者 ID を生成します。
**複数の利用者に呼び出し権限があり、別利用者の `context_id` が既知または共有される場合**、同じセッションとして扱うおそれがあります。異なる合成認証ヘッダーと同じ ID で同じ所有者になることを確認したもので、本番で他者の情報を取得した検証ではありません。

**暫定対処:** 共有利用者ごとの隔離が必要な A2A サービスとして利用せず、信頼できる単一の運用主体に利用を限定してください。**改善案:** 検証済みの利用者情報をセッションに結びつけ、セッション・タスクの取得や再開で所有権を確認します。自己申告のヘッダーを認証情報として信頼しません。

## 改善の順序と構成

| 順序 | 項目 | 改善方針 |
|---|---|---|
| 1 | A01・A05・A06 | PR の識別と監査の確認範囲を正しく扱い、根拠不足を未確認として返す |
| 2 | A02・A04 | GitHub 書き込みの予算・排他・再試行を共通化する |
| 3 | A07・A08・A09 | エンジン差、期限、条件を取得結果に保持する |
| 4 | A10・A11 | 設定定義をローカル・配置・doctor で共有する |
| 5 | R01・R02・権限範囲 | 実行結果保存と利用者境界を運用条件に合わせ、必要な秘密だけへアクセスを許可する |

[GCP の監査処理](../app/providers/gcp/security.py) は IAM・鍵・Cloud Run・Cloud SQL に分け、取得処理と判定処理を分離する方針です。
取得結果には確認範囲・取得エラー・時刻・条件を残します。[GitHub ツール](../app/tools/issues.py) は Issue 操作、PR の証拠取得、レポート発行に分け、書き込み制御を共通にします。
修正の検証済み判定は PR・SHA・CI・配置・観測期間の証拠をコードで確認し、モデルは証拠取得と説明を担当する構成を検討します。
`ToolScope` は取得件数・対象・引数を検証します。プロンプトにある呼び出し回数・実行時間の目安を、実行全体の予算として制御する対応は別途必要です。

[bootstrap](../scripts/gcp/bootstrap.sh#L33) は秘密の読み取り権限をプロジェクト全体へ付与します。
GitHub トークンだけが必要なら、そのシークレットへ限定する改善が必要です。本番に現在付与されている権限を確認した結果ではありません。[Secret Manager の最小権限](https://docs.cloud.google.com/secret-manager/docs/access-control)

変更時は各再現条件を回帰テストに加え、同時実行、取得失敗、未確認の報告、実行結果の保存を通しで確認します。
単体テスト、実モデルの評価、認証付きの配置確認、定期実行の完了確認はそれぞれ別の検証です。
