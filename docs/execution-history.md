# 実行履歴と証拠の保存

English: [execution-history.md](en/execution-history.md)

[Issue #8](https://github.com/atsuki-sakai/cloud-ops-team/issues/8) の保存層と既存ジョブへの接続を実装しています。
`app/core/execution_store.py` はクラウドやモデルに依存しない SQLite 保存層です。
呼び出し側が指定する保存先に実行履歴と保護済み証拠を保存し、再起動後に同じファイルから参照できます。

`OPS_EXECUTION_DB_PATH` を設定すると、既存の登録ジョブと自然言語受付から呼ばれる担当ジョブを同じ台帳へ記録します。
未設定時は保存層を開かず、既存の実行方式を維持します。会話の受付だけで担当ジョブが実行されない場合は台帳へ登録しません。
Issue #8 全体の完了、クラウド上の永続化、運用公開の合格は別に確認する必要があります。

## 既存ジョブで有効にする

```bash
OPS_EXECUTION_DB_PATH=/srv/cloud-ops-private/history.sqlite3 make run JOB=access_watch
```

保存先の親ディレクトリを作成できる場所を選んでください。保持期間・サイズ上限の設定は[設定一覧](configuration.md)にあります。
各ジョブは処理開始前に実行を登録し、収集結果を候補絞り込みやモデル用サイズ制限より前に保護して保存します。
モデルのツール・説明・既存の証拠スナップショットに保存先や証拠参照を追加する変更はありません。
収集した証拠全文は自動的にモデルへ提示されず、後続ページをモデルから読む機能は別の接続作業です。

Cloud Scheduler のジョブ名と予定時刻、または標準 Pub/Sub push の subscription と messageId を不透明な配信 ID に変換します。
Scheduler の予定時刻は再試行でも同じになる[公式仕様](https://docs.cloud.google.com/scheduler/docs/creating)を利用します。
ヘッダー・本文は認証の代わりにせず、既存の OIDC／プラットフォーム認証を通過したジョブだけが台帳に入ります。
有効な配信情報がない HTTP/SSE・A2A・直接実行は ADK invocation 単位です。
subscription の欠落・空値では messageId だけから配信を確定しません。
保存を有効にした trigger の本文は 64 KiB に制限し、識別に使った本文をそのまま既存ハンドラーへ渡します。

同じ対象・ジョブ・配信の再実行は結果イベントに `duplicate` と既存の実行 ID／状態を返し、収集・モデル・報告の副作用を再実行しません。
ADK の trigger HTTP 応答は、ジョブ失敗や重複時も受領成功の 200 になる場合があります。HTTP 応答だけで判断せず、台帳・結果イベントで確認してください。
同じ配信 ID の期間や設定が変わった場合は拒否します。`full` は最初の重複ジョブで停止し、後続の未実行ジョブを自動再開しません。
失敗・中断・実行中の記録も再配信だけでは再開しないため、運用者が状態を確認して新しい実行として開始してください。
異なる配信や別 invocation での GitHub 起票重複まで抑止する保証ではありません。

保存失敗は成功へ変換せず、後続の収集や GitHub 書込みを止めます。
終了記録・最終レポートの保存失敗も障害状態を保持します。終了記録を保存できた場合は、最初の保存障害を固定の例外分類で記録し、例外メッセージやトレースは含めません。
収集が別スレッドで待機中に取消された場合、その呼出自体を強制終了はできませんが、戻った結果の保存と次の収集を拒否します。
`TimeoutError` は `timed_out`、取消・ストリーム中断は `interrupted` として最小の終了記録を試みます。
保存先自体が故障して終了状態も書けない場合やプロセスの強制終了では、`running` が残り得ます。自動回復・再配信による再開は実装していません。

収集不足・未提示・切り詰めは `partial`、報告ツールの失敗は `report_failed` として最終テキストと状態を保存します。
`succeeded` は取得・提示・ストリーム終了で観測したプログラム上の正常終了です。モデルの理解、根拠の妥当性、業務上の完了を保証しません。
共有予算の強制は Issue #19、モデルの品質と公開判定は Issue #20 で追跡します。

## 保存先と保護の条件

- 呼び出し側が明示した専用ディレクトリと DB ファイルを使用します。未設定時にメモリや一時領域へ代替保存する経路はありません。
- 所有者だけがアクセスできるディレクトリと DB が必要です。共有権限やシンボリックリンクを拒否し、SQLite の補助ファイルも同じ保護範囲に置きます。
- 並行実行で正常に削除される補助ファイルの消失・リンク数 0 は許容します。DB 本体はリンク数 1 を必須とし、補助ファイルでも不正な型・所有者・権限や複数のリンクを拒否します。
- 上位ディレクトリも現在の OS ユーザーまたは root の所有に限定します。グループ・他者に書込み可能な上位ディレクトリは sticky bit が必要です。これにより、非 sticky の共有領域から専用ディレクトリごと差し替える経路を拒否します。root 所有の sticky な一時領域は許可しますが、一時領域が永続保存先になるわけではありません。
- 権限不足、保存先の故障、サイズ上限などの失敗は例外として呼び出し側へ返します。保存成功や調査成功には変換しません。
- 同じファイルを再度開いた場合の永続性を提供します。Cloud Run の一時ファイルシステムを再配置・複数インスタンスに耐える保存先と扱わないでください。クラウド用の保存先・権限・バックアップは今後の接続時に設計します。
- SQLite ファイルへの直接アクセス権を持つ利用者は内容を読めます。対象ごとの API 検証は呼び出しミスを防ぐもので、同じ OS ユーザー間の認可や DB 暗号化の代わりにはなりません。
- 現在の OS ユーザーと root は信頼する前提です。同じ OS ユーザーが故意にパスや DB を差し替える行為は、この保存層の権限境界に含みません。

## 実行の識別と状態

`ExecutionScope(provider, target)` をすべての読み書きに渡します。
同じイベントでも provider・target・job が違えば別実行です。
`create_run` はイベントの重複をトランザクションで判定し、既存実行と新規作成の違いを返します。
呼び出し側は既存実行を返された際に処理を再開・再実行してよいか判断する必要があります。
この API をジョブ接続で利用すると同一配信の再実行を抑止します。配信が異なる GitHub 起票の重複制御は従来どおりです。

台帳は実行 ID、予定時刻、契機、設定版、シナリオ版、相関 ID、開始・終了時刻を保持します。
起動中・実行中・成功・失敗・期限超過・取得不十分・報告失敗・中断を区別し、
終了状態から実行中や成功へ戻す更新を拒否します。
実行中の取消は接続側で中断として記録します。強制終了の検知や放置された実行の回復には別の監視処理が必要です。

明示した保存先を使う最小例です。親ディレクトリを作成できる場所を選び、
実運用では永続領域のパスへ差し替えてください。

```python
from app.core.execution_store import ExecutionScope, ExecutionStore

scope = ExecutionScope("gcp", "example-project")
store = ExecutionStore("/srv/cloud-ops-private/history.sqlite3")
run, created = store.create_run(scope, "error_watch", "example-event-1")
if created:
    store.transition_run(scope, run.run_id, "running")
    evidence = store.put_evidence(
        scope,
        run.run_id,
        "example-source",
        "Protected test evidence",
        media_type="text/plain",
        protection_confirmed=True,
        acquisition_complete=True,
    )
    page = store.read_evidence_page(
        scope, run.run_id, evidence["ref"], evidence["version"], page_size=256
    )
    # Record actual model presentation or citation separately when observed.
    store.transition_run(scope, run.run_id, "succeeded")
```

この例の `succeeded` はサンプル処理の終了です。実際のジョブでは必要な取得・調査・報告を確認してから状態を確定します。

## 証拠の保存とページ取得

呼び出し側で取得・マスク・保存許可を確認したテキストと JSON のみを受け付けます。
保存時にも既存の伏せ字処理を適用しますが、伏せ字だけで任意の情報を安全と認定しません。
画像・動画・生の DOM・通信記録の保護はこの保存層の対象外です。
許可される対象、取得量、保管範囲を収集側で制限してください。

証拠は実行・対象・取得元・版と結び付けて保存します。
返すメタデータは不透明な参照、ハッシュ、サイズ、保管状態などで、本文や保存先パスを含みません。
サイズ上限を超えた本文を無断で切り詰めて保存完了と扱いません。
API 取得範囲とその完全性・不足理由は、保管できた範囲と別に保持します。
伏せ字を適用した後の本文を正本とし、取得時の秘密値を再取得できるという意味の「全文」ではありません。

`read_evidence_page` は対象・実行・証拠参照・版を検証し、指定サイズのページを返します。
続きの cursor は保存先の秘密鍵で署名し、別対象・別実行・別証拠・別版への流用と改ざんを拒否します。
範囲は Unicode の文字位置で、保存量の上限は UTF-8 バイト数です。
返却範囲・残りの有無・次の cursor を確認し、取得したページだけをモデルへ渡してください。

`record_evidence_use` で `presented`（提示）と `referenced`（根拠として参照）を別々に記録します。
既存ジョブでは `get_collected_evidence` が実際に返した限定スナップショットと追加調査の返却結果だけを、別証拠として提示記録にします。
元の取得結果の全文を提示済みとは扱わず、根拠としての参照を自動で付けません。
ページを読むだけで確認済みにはしません。保存層は、モデルが実際に理解・調査したことを証明しません。
呼び出し側が実際の提示や根拠参照を観測して記録し、未読・未確認の範囲を保持する必要があります。

## 保持期限、削除と予算記録

保持期間と証拠ごとのサイズ上限は保存層の設定で指定します。
既定は保持 30 日・証拠 1 件あたり 8 MiB、ページは 4,096 文字（上限 16,384 文字）です。
期限を過ぎた本文は読み出せません。`purge_expired(scope)` は指定対象の期限切れ本文を削除し、
`delete_evidence` は個別の本文を削除します。台帳と削除理由は残し、欠損を完全取得に変更しません。
呼び出し側で期限切れ削除を定期実行する必要があります。
DB のバックアップ、ストレージのスナップショット、媒体上の残存データの物理消去は別途管理してください。

`save_budget_snapshot` は共有予算の上限・消費・停止理由・未確認事項を記録する境界です。
回数・費用・時間の制限や並行処理の予約・集計はまだ強制しません。
その実行時制御は Issue #19 で接続し、到達時に証拠と未完了理由を保存する契約へつなげます。
