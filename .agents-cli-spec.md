# Agent Spec — cloud-ops-team

## Overview
An AI operations team for a cloud environment. A leader agent dispatches scheduled jobs (or natural-language requests) to three
specialists that investigate with read-only tools and hand work to humans through GitHub issues:

- **error_watch (SRE)** — groups error logs by fingerprint, correlates with 5xx rates, failing scheduled jobs and recent
  deployments, files `[ops/error]` issues with a root-cause hypothesis (recurrences become comments).
- **security_audit (cloud security)** — monthly: IAM, credentials, compute, databases, network, security services, posture
  findings, image CVEs, EOL, CISA KEV, web threat research; files critical/high findings and a monthly report.
- **pr_review (release manager)** — weekly: verifies linked PRs are merged, CI is green and the error did not recur; labels
  `ops:verified` / `ops:stale`; weekly report.

The cloud is pluggable (`OPS_CLOUD_PROVIDER`): agents use 18 cloud-neutral capability tools implemented by providers.
Google Cloud is implemented; AWS and Azure are skeletons that return `not_supported`.

## Language
`python` (ADK 2.11, agents-cli 1.9)

## Example Use Cases
| Input | Expected behaviour |
|---|---|
| `{"data": {"job": "error_watch", "hours": 24}}` (daily) | Group errors → investigate up to 5 groups → file or comment → report |
| `{"data": {"job": "monthly_security_audit", "kev_days": 30}}` | Run every check once → file critical/high → monthly report issue |
| `{"data": {"job": "weekly_pr_review", "days": 7}}` | Verify each open team issue → `ops:verified` / `ops:stale` → weekly report issue |
| "check the errors of the last 3 days" | Delegate to error_watch, answer in the report language |
| "restart the worker service" | Refuse (read-only) and propose an issue |

## Tools Required
- Cloud capabilities (provider-backed, read-only): logs ×4, services, deployments, scheduled jobs, databases, request error
  rates, alerting, IAM, credentials, compute, databases audit, network, security services, security findings, image scans
- Cloud-neutral: CISA KEV, endoflife.date, Google Search-grounded research (one bounded call), repository posture (GitHub)
- GitHub: issues (create, comment, label, close when allowed), search, PRs, workflow runs

## Constraints & Safety Rules
- Never change cloud resources; GitHub writes limited to issues, comments and labels; closing requires `OPS_AUTO_CLOSE_ISSUES=true`.
- `OPS_DRY_RUN=true` by default (previews only); `OPS_MAX_ISSUES_PER_RUN` caps new issues; one recurrence comment per cooldown.
- Redact tokens, keys, e-mail addresses, card numbers and public IPs; environment variables by name only.
- Headless (JSON) runs never ask questions; `error` / `api_disabled` / `not_supported` are reported, not hidden.

## Success Criteria
- Each job reaches the right specialist and its tool sequence; reports cite evidence and mark dry-run previews.
- Change requests are refused with an issue proposal.
- Existing issues are recognised across versions (golden fingerprint tests) and per target.
- Eval: `ops_report_rubric` ≥ 4.5 on `tests/eval/datasets` and the hold-out set.

## Architecture & Sub-Agents
root `cloud_ops_team` → sub-agents `error_watch`, `security_audit`, `pr_review`, all `mode="single_turn"` (exposed as tools,
run inline, streamed and traced). Specialists are declared in `app/specialists/` (instruction, tools, jobs); routing table and
scheduler jobs are generated from that registry. Project knowledge comes from `config/ops-context.md`. Tools in `app/tools/`, providers in `app/providers/` (`base.py` contract, `gcp/`, `aws/`,
`azure/`, entry point `cloud_ops_team.providers`), shared helpers in `app/core/`. See `docs/architecture.md`.

## Deployment
Google Cloud: Cloud Run (private, dedicated runtime service account, 1800 s timeout, scale to zero) + Cloud Scheduler HTTP jobs
with OIDC (`scripts/gcp/*`). Default schedules: error watch daily 08:00 (24 h window), weekly review Monday 09:00, monthly audit
on the 1st 09:00 — all configurable.
